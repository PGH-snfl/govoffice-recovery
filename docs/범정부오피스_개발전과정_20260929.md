## 1. 처음 무엇을 하려고 시작했는가

출발점은 기존 범정부오피스 실행 파일과 추출·역컴파일 자료를 확인하고, 실행 파일 안의 실제 기능을 수정 가능한 Python 소스로 복구하는 일이었다. 처음부터 새 인공지능 문서 작성기를 만드는 작업은 아니었다. 사용자는 폴더 상태, 역컴파일 결과, Python 코드가 저장된 형식, 복구 방식과 내부 구조를 차례로 확인했고, 복구 자료와 새 개발 프로젝트를 보기 쉽게 분리하도록 요청했다.

복구 우선순위는 대화에서 **한글 먼저, Excel과 PowerPoint는 나중**으로 정해졌다. 오래된 `docs/WORKFLOW.md`에는 다른 우선순위가 남아 있으므로 현재 사용자 결정과 구분해야 한다. 원본 안에 Excel·PowerPoint 관련 모듈이 있다는 사실과 해당 기능을 새 프로그램에서 모두 사용할 수 있다는 주장은 별개다.

그 뒤 사용자가 원하는 방향이 구체화됐다. 한글 기본 기능은 공통으로 사용하고, 기관별 기능은 기관 패키지로 분리하며, 개인 정보와 서식을 저장해 반복 입력을 줄이는 내부 업무 도구를 만들고자 했다. 최종 목적은 **사용자가 원하는 양식을 고르고 작성 주제와 세부 내용을 입력하면, 프로그램이 작성요령을 준비해 AI에 전달하고, 결과를 원래 서식에 맞춰 한글 문서로 만드는 것**이다.

이 프로그램은 **내부 사용용**이다. 대외 공개나 상용 배포를 전제로 한 프로젝트가 아니다. 저장소의 `packaging/` 및 일부 문서에서 쓰는 ‘배포’는 내부 PC 실행 환경을 묶는 설치·운영 작업으로 이해해야 한다. 기관 라이브러리 내려받기, 기관 인증, 계정별 연결 등 논의된 기능을 모두 이미 완성된 서비스라고 간주하지 않는다.

## 2. 원본 분석과 소스 복구의 출발 자료

기존 정적 분석 기록에 따르면 `범피스1303.exe`는 Python 3.13 기반 Windows 64비트 프로그램을 PyInstaller로 묶은 실행 파일이었다. PyInstaller는 Python 코드와 실행에 필요한 자원을 한 프로그램으로 포장하는 도구다. 자동 역컴파일에는 pycdc를 사용했다.

9월 3일 정리 문서에 기록된 원본 분석 규모는 아카이브 항목 4,309개, 코드 객체 4,174개, 자동 역컴파일된 메인 코드 약 12,377줄, PNG 이미지 3,326개, HWP 15개, HWPX 5개다. 이는 당시 분석 기록의 집계이며 이번 노션 정리 작업에서 원본 실행 파일 전체를 다시 추출해 센 수치는 아니다.

처음에는 코드가 모두 정상적인 `.py` 소스로 존재한 것이 아니었다. 원본의 `.marshal` 파일에는 Python 코드 객체와 바이트코드가 들어 있었고, 자동 역컴파일 결과에는 제어 흐름이나 인자가 불완전한 부분이 있었다. 그래서 자동 산출물을 곧바로 복구 완료본으로 쓰지 않고, 문자열·가져오기 목록·함수 목록·디스어셈블 결과와 함수별로 비교했다. 디스어셈블은 실행 명령을 사람이 읽을 수 있는 형태로 풀어 보는 분석이다.

복구 절차는 원본 모듈 선택 → 코드 객체·명령·문자열 분석 → 자동 역컴파일과 비교 → 공개 함수 이름과 인자 유지 → 일반 Python 소스 작성 → 문법·인터페이스 검사 → 모의 객체 시험 → 실제 한글 비교 시험 순서였다. 판단할 수 없는 분기는 추측으로 감추지 않고 별도 상태로 남기는 것을 기준으로 삼았다.

## 3. 프로젝트를 분리한 이유와 실제 구조

원본 증거, 복구 코드, 새로 만드는 기능이 섞이면 어떤 동작이 원본에서 나온 것인지 알기 어려웠다. 또한 새 사용자 기능을 원본 복구 코드에 직접 넣으면 원본과의 비교가 깨지므로 영역을 나눴다.

```text
범정부오피스/
├─ 범피스1303.exe                  원본 실행 파일
├─ 범피스1303_분석/                추출 자원·marshal·자동 역컴파일·분석용 런타임
├─ recovery_analysis/             다시 생성할 수 있는 분석 자료
├─ recovered/                     원본 동작과 공개 함수의 복구 소스
├─ docs/                          구조·작업 기준·연구개발 작성 기억
└─ new_project/                   실제 신규 프로그램
   ├─ src/govoffice/
   │  ├─ app/                    실행 구성
   │  ├─ domain/                 업무 데이터 모델
   │  ├─ ports/                  기능 연결 규약
   │  ├─ services/               서식·개인정보·문서 작성 흐름
   │  ├─ adapters/               한글·복구 코드·외부 AI 연결
   │  ├─ institutions/           기관별 패키지
   │  ├─ presentation/           화면 모델
   │  └─ runtime/recovered_hwp/   검증 복구 소스의 실행용 사본
   ├─ config/                    개발 실행용 저장 데이터와 등록 양식
   ├─ ai_response_library/       저장된 AI 응답 묶음
   ├─ development/               테스트·도구·보고서·예시·화면 자료
   └─ packaging/                 내부 실행 환경 구성
```

새 업무 코드가 `recovered/`를 직접 가져오지 않고 연결 어댑터를 거치도록 했다. 어댑터는 서로 다른 구현 사이를 연결하는 얇은 계층이다. 현재 실행용 복구 코드는 `runtime/recovered_hwp/`에 사본으로 들어가며, 원본 복구 저장소와 새 프로그램의 변경 범위를 구분한다.

화면도 원본 버튼 콜백에 모든 기능을 다시 넣는 방식에서 분리했다. 현재 주요 흐름은 WPF(Windows Presentation Foundation, Windows 화면 구성 기술) 화면 → JSON(JavaScript Object Notation, 구조화된 데이터 형식) 명령 → Python 백엔드 → 업무 서비스·어댑터 → 한글 자동화다. 화면은 입력과 진행 상태를 담당하고, 문서 처리와 저장은 뒤쪽 코드가 담당한다.

## 4. 어느 정도 복구됐고, ‘복구 완료’는 무엇을 뜻하는가

현재 `recovered/복구현황.md`에서 확인되는 소스 복구 수는 한컴기본 310개, 한컴1 293개, 한컴2 98개, 기본한컴 810개로 총 **1,511개**다. 현재 진입점은 미복구 바이트코드를 직접 실행하지 않는 상태로 기록되어 있다. 과거의 ‘소스 1,411개 + 바이트코드 호환 100개’는 중간 단계 수치다.

그러나 소스가 존재한다는 것과 원본과 같은 출력이 검증됐다는 것은 다르다. 9월 3일 비교 기록은 정적 명령 구조 일치 1,080개, 실제 한글 실행 결과 일치 339개, 같은 오류 4개, 별도 검증 대상 88개였다. 따라서 정상 동등성이 확인된 범주를 말할 때는 1,419개와 같은 오류 4개를 구분해야 한다. 현재 실행용 사본 집계에는 1,423개가 verified로 묶이지만 그 안에 same_error 4개가 포함된다. same_error는 정상 작동 완료라는 뜻이 아니다.

초기 비교에서는 동적 완전 일치 141개, 출력 불일치 210개, 시간 초과 73개 등이 나왔고, 이후 잘못된 시험 문서, 출력 정규화, 빠진 기본 인자와 실제 구현 누락을 구분해 고쳤다. 함수 인자의 끝쪽 기본값 188건을 보정한 이력도 있다.

대표 사례로 광주광산표지는 원본 10열×5행 구조·병합·테두리·문구를 복원했고, 마크다운응용은 재귀와 새 창 반복 생성 문제를 정리했다. 경남도행사장은 여백·행 높이·열 폭·좌석 호출 순서를 맞췄다. JSON 변환처럼 특정 선택 데이터가 있어야 동작하는 기능은 유효한 입력과 빈 문서 조건을 나누어 시험했다. 원본과 같은 함수 이름만 있다고 모든 문서에서 바로 실행되는 것은 아니다.

## 5. 실제 버튼과 실행 가능한 기능을 구분하게 된 과정

사용자는 원본 안에서 한글 명령을 여러 번 사용하는 복합 기능을 찾고, 비슷한 기능을 제외하며, 원본 화면에서 어느 탭·어느 버튼인지 함께 제시하라고 요구했다. 보기변환·비전표·분배 등을 직접 시험할 수 있는 예시 문서와 버튼을 띄우라는 요청도 이어졌다.

이 과정에서 실제 화면에 없는 기능이나 확인되지 않은 버튼을 설명한 것에 대한 강한 지적이 있었다. 이후 기록과 기능 목록에는 **원본 함수 존재, 화면 버튼 존재, 버튼 연결 복구, 입력 조건 충족, 실제 실행 성공**을 서로 구별해야 한다는 원칙이 중요해졌다. ‘함수 이름을 찾음’을 ‘사용자가 지금 누를 수 있는 버튼’으로 설명하면 안 된다.

9월 3일 버튼 연결 보고서는 원본 버튼 연결 2,100개에서 연결·레이아웃 불일치 0건을 기록했다. 일반 기능 버튼 304개와 기관 기능 화면도 기록되어 있다. 이 수치는 연결 구조 검사이며 2,100개를 각각 실제 문서에서 모두 클릭해 완성 출력을 확인했다는 뜻은 아니다. 이번 개인 기록에서는 보기변환·비전표·분배의 개별 실기 성공을 새로 입증하지 않았다.

## 6. 기관별 기능과 서울과학기술대학교

사용자가 제안한 구조는 공통 한글 기능을 메인 프로그램에 두고, 기관의 특수 기능은 기관 라이브러리에 넣는 방식이었다. 기관 등록 후 해당 기관의 탭을 만들고, 공통 기능을 받아 쓰며 자체 함수와 서식을 추가하는 방향으로 정했다. 기관 인증 후 기관 기능을 추가하는 운영 구상도 있었다.

실제 파일 구조에서는 기관별 manifest.json에 표시 이름·실행 메서드·자원 경로를 기록하고, 기관 폴더에 아이콘과 서식을 분리했다. 기존 메인 코드에 하드코딩된 기관 기능을 이 구조로 옮기는 작업을 진행했다. 문서화된 집계는 등록 기관 24개, 정리된 기관 기능 503개, 무인자로 바로 실행 가능한 기능 200개, 원본 화면 입력값을 연결하는 처리가 더 필요한 기능 303개다. 이 값은 기관 기능 카탈로그 집계이며 원본 API 1,511개와 다른 기준이다.

서울과학기술대학교는 `seoultech` 패키지로 추가하고 ‘교직 → 서울과기대’ 경로에 연결했다. 선택 영역 전체 디자인 서식 프리셋과 연구개발 문서 작성 기능을 이 기관 영역에 추가했다. 사용자 요구에 따라 기관 프리셋은 기관 탭에, 자주 사용하는 기관 양식은 상단에, 기관 자체 기능은 공통 즐겨찾기 아래에 구분하는 방향을 잡았다.

기관 라이브러리 구조가 있는 것과 원격 다운로드 서버·실제 기관 인증 서비스·관리자 승인 체계가 완성된 것은 별개다. 현재 확인 자료만으로 이러한 운영 서비스까지 완료했다고 기록하지 않는다. 비용도 로컬 저장 기능과 외부 AI 계정 사용량, 한글 설치 환경 등 실제 필요한 요소를 구분해야 하며 과거 대화만으로 현재 요금이나 비용을 확정하지 않는다.

## 7. 즐겨찾기·기본 기능·프리셋의 역할

즐겨찾기는 자주 실행하는 기능의 바로가기다. 기관 탭에서 기본 기능 즐겨찾기를 위에, 기관 자체 기능을 아래에 두고, 개인 탭에서도 사용자 기능을 확인할 수 있도록 요구했다. 저장 위치는 `config/favorites.json`, 화면 모델은 `presentation/institution_tab.py`, 저장 구현은 `adapters/json_favorites.py`로 나뉜다. 기능 식별자와 필요한 입력 구조를 연결하며 순서 변경을 저장한다.

기본 기능은 글자 크기 변경처럼 꼭 필요한 값이 있으면 그 값만 입력받는다. 이미 값을 포함한 프리셋은 바로 실행하는 방향이다. 같은 질문을 실행할 때마다 반복하거나 여러 확인창을 거치지 않도록 하는 것이 사용자 경험의 기준이었다.

프리셋의 의미도 대화 중 확장됐다. 글꼴과 글자 크기만 저장하는 정도로는 쓸모가 부족하고, 표의 첫 행·첫 열·나머지 셀마다 다른 정렬과 글자 크기, 병합·테두리·배경까지 저장해야 한다는 요구였다. 따라서 프리셋은 단순한 ‘굴림 11pt’ 설정 목록에서 **선택된 영역의 전체 디자인과 내용 구조를 재사용하는 기능**으로 발전했다.

## 8. 서식 복사 요구가 바뀐 순서와 최종 방향

처음에는 문서의 내용은 제외하고 서식을 저장하는 방식을 논의했다. 입력이 필요한 부분을 따로 표시하고, 제거되는 내용 대신 ‘여기에 어떤 값을 넣어야 하는지’를 알려주는 안내를 넣는 구상도 있었다. 프리셋을 출력할 때 빈칸만 만들기보다 ‘굴림체 11pt’처럼 서식 자체를 설명하는 예시를 넣자는 요구가 나왔다.

이후 사용자는 제목은 유지하고 이름은 홍길동, 날짜는 출력일, 전화번호는 예시 번호로 바꾸되 원래 빈칸은 비워 두도록 요청했다. 쪽 크기·방향·여백 등 원본의 쪽 서식도 함께 가져오도록 범위를 넓혔다. 하지만 문서 전체를 저장하면 단순 파일 복사와 다르지 않다는 지적에 따라 **사용자가 선택한 영역만 저장**하도록 확정했다.

다음 요청에서 원본 내용은 전부 그대로 복사하는 방향으로 바뀌었다. 이어 개인 탭에 저장된 사용자 정보만 지정된 위치에서 텍스트로 교체하도록 연결했다. 따라서 과거의 일괄 익명화 요구를 현재 기본 동작이라고 설명하면 안 된다. 최신 프리셋의 기본은 선택 영역의 원래 내용·디자인 보존이며, 확인된 개인정보 필드만 저장값과 연결한다.

한글 선택 영역은 HWPML(Hangul Word Processor Markup Language, 한글 문서 구조를 표현하는 XML 계열 형식)의 조각으로 저장한다. `GetTextFile("HWPML2X", "saveblock")`으로 읽고, `SetTextFile(..., "HWPML2X", "insertfile")` 등으로 삽입한다. 글꼴·문단·표·셀 병합·테두리·개체와 선택 영역이 속한 구역의 쪽 설정을 보존한다. `.hml`과 프리셋 정의 `.json`은 한 쌍으로 저장하며, 한쪽만 저장되는 실패를 방지한다.

## 9. 개인 정보 저장과 대표필드·하위필드

기관과 별도로 사용자마다 다른 이름·전화번호·이메일을 저장하는 개인 탭을 만들었다. 추가 정보는 대표필드, 하위필드, 별칭, 여러 값, 기본 출력값으로 표현한다. 이름이 바뀌어도 연결이 유지되도록 화면에 보이는 이름과 별개로 안정된 고유 식별자를 둔다. 저장소는 `config/user_profile.json`이다.

대표필드와 하위필드는 같은 필드 자료형이며 부모 식별자로 계층을 만든다. 예를 들어 ‘연구자 → 성명’과 ‘기관 → 연락처’처럼 연결한다. 하나의 필드에 여러 값을 보관하고 기본값을 지정할 수 있다. 같은 실제 값이 여러 역할에 쓰일 수 있기 때문에 단지 값이 같다는 이유로 다른 역할을 합쳐 버리면 안 된다.

사용자는 대표필드를 다른 대표필드로 끌면 기존 하위 구조도 함께 이동하고, 하위필드는 다른 대표필드 아래로 옮길 수 있도록 요구했다. 대표필드 체크박스는 중간 상태가 없는 켜기·끄기 두 단계로 바꿨다. 점수가 낮아 기본 체크가 꺼진 후보는 아래로 보내되, 체크된 그룹과 체크되지 않은 그룹 안의 원래 순서는 유지하는 방향이었다.

‘대표필드 끌기’는 드래그 모션만 보이고 이동이 적용되지 않는 문제가 반복 보고됐다. 특히 같은 이름의 대표필드를 서로 다른 그룹으로 만들고 이름 충돌로 이동을 거부하는 흐름이 문제로 지적됐다. 선택 영역을 처음 읽을 때 같은 대표필드의 하위필드와 데이터를 기존 대표필드에 모으도록 요구가 바뀌었다. 다만 서로 다른 저장 화면의 규칙은 구분해야 한다. 후보 정리에서 같은 대표필드를 모으는 것과, 저장소에서 같은 부모 아래 이름·별칭 충돌 또는 자기 하위로의 순환 이동을 막는 것은 별도 규칙이다.

개인 데이터는 트리 형태의 표로 보여 주고, 열 머리글 경계 드래그로 너비를 바꾸며, 항목·값을 더블클릭해 수정하도록 개선했다. 데이터 관리창에서는 필드나 값 우클릭, 값 추가·기본값 지정·삭제·이동을 지원한다. 문서 작성 화면에서 임시로 수정한 값은 그 작업에만 반영하고 기본 사용자 프로필을 자동으로 덮어쓰지 않는다.

## 10. 표 선택을 읽었는데 표 전체가 잡힌 문제

여러 표와 본문이 섞인 문서에서는 선택 영역, 항목명, 값의 관계를 정확히 읽는 것이 중요했다. 사용자가 한글에서 몇 개 셀만 파랗게 선택했는데 내보내기 결과가 표 전체를 포함하는 문제가 확인됐다.

2026-09-09 실제 검증에서는 HWPML2X·TEXT·UNICODE·HTML의 saveblock이 모두 선택 셀 대신 둘러싼 표 전체를 반환했다. 따라서 서로 다른 내보내기 형식을 비교하는 것만으로는 선택 범위를 보증할 수 없었다.

개인정보 가져오기에서는 선택 전용 스캔 `InitScan(7, 255)`의 텍스트와 현재 셀 주소를 함께 사용해 유일한 사각 범위를 찾고, 원래 표 구조에서 그 셀들만 남기도록 했다. 시험에서 전체 151셀 중 선택한 28셀만 남았고 분석 후보가 48개에서 12개로 줄었다. 선택 밖의 연구개발기간·연구개발비는 제외됐다.

같은 글이 여러 곳에 있어 범위가 여러 개 성립하거나 병합 셀을 잘라야 하는 경우에는 임의의 위치를 선택하지 않는다. 이 검증은 개인정보 가져오기 경로의 실제 선택 범위 검사이며, 모든 중첩 표와 모든 프리셋 선택 방식의 완전성을 보증한 것은 아니다.

## 11. 창·작업 문서·사용자 편의 요구

원본처럼 떠 있는 작은 창뿐 아니라 Windows 작업표시줄에서 창을 표시·최소화·복원할 수 있는 일반 프로그램 동작을 원했다. 항상 위에 고정할지는 사용자가 정하고, 고정 상태에서도 위치를 옮길 수 있어야 한다는 구상도 있었다. 이러한 논의 항목과 각 창의 실제 옵션 구현 여부는 별도 확인 대상이다.

현재 작업 문서는 메인 화면 최상단에서 제목·경로·편집 가능 여부·수정 여부·표시 상태를 확인하도록 연결했다. 사용자가 적용 대상을 알 수 있게 하고, 프로그램이 직접 불러온 관리 문서와 사용자가 따로 연 문서를 구분한다. 서식을 새 문서에 출력할지 현재 문서에 적용할지에 대해서도 대상 문서를 분명히 해야 한다는 요구가 있었다.

한 창이 열려 있어도 다른 관리창을 조작할 수 있게 바꾸었다. 기관·서식 프리셋·즐겨찾기·개인정보 관리·문서 작성 창은 비모달 Show()로 열고, 같은 창을 다시 요청하면 기존 창을 활성화한다. 비모달은 그 창이 열려 있어도 다른 창의 조작을 막지 않는 방식이다. 삭제 확인·짧은 값 편집·파일 선택처럼 결과를 받아야 하는 작은 창은 모달 방식을 유지한다.

색상은 보라색 계열로 맞추되 강한 그라데이션은 피하라는 요구가 있었다. 진행은 보라색, 완료는 초록색, 중단·재개 가능은 주황색, 오류는 빨간색으로 구분했다. 진행률은 완료한 소주제 비율이며 AI 내부 사고 진행률이나 정확한 남은 시간을 추정해 표시하는 값이 아니다.

## 12. 반복된 ‘멈춤’은 한 가지 원인이 아니었다

### 12-1. 창 이동 중 자동 조회가 겹치는 경로

개인정보 결과 창을 끌어 옮길 때 멈춘다는 보고가 있었다. 결과 창의 ShowDialog() 중에도 문서 상태 조회 타이머와 선택 감지 타이머가 계속 실행되는 경로를 확인했다. 선택 분석부터 결과 창 종료까지 해당 자동 조회를 멈추고, 이미 대기열에 들어온 조회도 건너뛰며, 종료 시 이전에 켜져 있던 타이머만 복원하도록 했다.

새 문서 작성 창에도 같은 문제가 남아 있어 9월 10일 공통 보호를 확장했다. 창 이동·크기 변경 시작과 종료를 감지해 자동 조회가 PowerShell 이벤트로 진입하기 전에 차단했다. 문서 상태, 선택 감지, 프리셋 상태, 직접 필드 선택, 작성 진행 조회의 다섯 경로에 적용했다. 문서 작성 자체는 화면 조회와 별도로 계속 진행되도록 했다.

이때의 증거는 불필요한 조회 경로와 모의 이동 상태에서의 차단 검증이었다. 사용자 PC 전체가 멈추는 모든 현상의 직접 원인과 완전 해소를 입증한 것으로 기록하면 안 된다.

### 12-2. 오류 출력 정체와 전체 요청 차단

9월 10일 별도 진단에서는 백엔드의 stderr(표준 오류 출력 통로)를 계속 읽지 않아 가득 차면 백엔드가 막힐 수 있음을 재현했다. 시험 프로세스가 256KiB의 오류 출력을 쓴 뒤 READY를 보내도록 하자 응답이 멈췄고, 오류 출력을 비우면 즉시 이어졌다. 이는 시험에서 재현한 공통 결함이며 사용자의 실제 실행에서 같은 양의 오류가 발생했다는 뜻은 아니다.

또한 한 번의 요청 시간 초과 뒤 BackendUnhealthy 상태가 유지되어 한글 기능뿐 아니라 로컬 개인 데이터 조회·수정까지 막히는 경로를 확인했다. 모호하게 끝난 한글 명령의 재실행 금지와, 문서에 손대지 않는 로컬 데이터 접근 제한을 구분해야 한다는 결론을 남겼다. 이 보고서 자체는 진단 단계이므로 해당 문서만 근거로 운영 수정 완료라고 쓰지 않는다.

### 12-3. 개인 탭 재진입 후 메인 창이 비활성화되는 실제 원인

9월 15일 진단에서는 ‘계산이 멈춤’과 다른 현상을 확인했다. 메인 창은 보였지만 Enabled=false, Hung=false였고, 다른 보조 창은 모두 보이지 않았다. 문서 상태 조회는 계속 정상 처리되고 있었다.

원인은 WPF Application 객체보다 메인 Window를 먼저 생성해 메인 창이 Application.Windows 관리 목록에 등록되지 않은 생성 순서였다. 첫 보조 창을 닫고 다음 보조 창을 열 때 메인 창이 비활성화된 채 새 창이 표시되지 않는 현상을 격리 재현했다.

Application을 먼저 만들고 메인 창을 MainWindow로 지정하며, 종료 조건을 메인 창 종료로 맞췄다. 수정 전에는 새 회귀 검사가 메인 창 소유 관계 오류로 실패했고, 수정 후에는 데이터·분석 창 12회와 중첩 수정창 6회의 열기·닫기를 서로 다른 이벤트 시점에서 통과했다. 이 결과는 특정 재진입 잠김 원인을 해결한 증거이며, 모든 향후 멈춤을 같은 원인으로 단정하는 근거는 아니다.

## 13. 한글 자동화 연결과 Automation 오류

COM(Component Object Model, Windows 프로그램 간 객체 호출 기술)은 범피스가 한글에 ‘문서 열기·글 입력·서식 변경·저장’ 명령을 보내는 통로다. API(Application Programming Interface, 프로그램 기능을 호출하는 규약)는 호출할 수 있는 기능의 약속이고, Automation 객체는 이 통로로 한글 기능을 제어하는 객체다.

원본에도 한글 COM 연결과 자동화 모듈이 있었다. 새로 한글 자체의 API를 만든 것이 아니라, 원본에서 확인된 기능을 복구하고 새 화면·문서 관리와 연결하는 계층을 보완했다. 단순 명령은 HAction.Run으로 실행하고, 크기·정렬·여백처럼 값이 필요한 기능은 Action과 ParameterSet으로 기본값을 읽어 일부 항목을 바꿔 실행한다. 복합 기능은 이런 명령을 순서대로 조합한다.

잘못된 문서를 수정하거나 닫지 않도록 프로그램이 관리하는 문서를 추적했다. 전용 인스턴스 생성, PID(Process Identifier, 프로세스 식별번호), 시작 시각, 창 핸들, DocumentID를 함께 확인하고, 수정 직전에 대상 문서를 활성화해 다시 검사한다. 사용자가 별도로 연 문서의 소유권을 추측해 종료하지 않도록 했다.

### 13-1. CLSIDToClassMap 누락

사용자 화면에 나타난 구체적 오류는 win32com.gen_py의 한글 타입 라이브러리 모듈에 CLSIDToClassMap이 없다는 것이었다. CLSID는 COM Class Identifier, COM 클래스 식별자다. 한글 기능용 자동 생성 Python 연결 코드가 불완전한 공유 캐시에서 선택되는 상태를 확인했다.

문서 변환·추출 프로세스에는 독립 캐시 처리가 있었지만 메인 백엔드에는 빠져 있었다. 메인 백엔드가 한글 라이브러리를 불러오기 전에 전용 임시 gen_py 경로를 설정하도록 고쳤다. 오류 동작·원문·환경은 진단 파일로 남기고, 공유 캐시 전체를 지우는 방식은 쓰지 않았다. 실제 메인 백엔드로 시험 문서 열기 → 관리 상태 확인 → 정상 종료를 검증했다.

그 뒤 ‘최종 출력본 한글 파일 열기’에서 같은 계열의 오류가 다시 발생했다. 원인은 이 버튼이 새 Python 프로세스를 만들고, 부모의 캐시 초기화가 그 프로세스에 자동 전달되지 않았기 때문이다. 출력본 열기 전용 실행부에도 초기화를 추가했다. 실제 버튼이 호출하는 명령 경로로 파일 경로 일치·창 표시·편집 가능 상태를 확인했다. 작성 실패와 완료 후 열기 실패를 구분한 사례다.

### 13-2. 보안 모듈 등록 거부는 다른 오류

9월 29일에는 FilePathCheckerModuleExample의 RegisterModule=False가 출력 생성을 막았다. DLL(Dynamic-Link Library, 동적 연결 라이브러리) 경로, 비트수, 현재 사용자 등록과 한글 프로세스 상태를 확인해야 하는 별도 문제다. 모든 Automation 실패를 캐시 문제 하나로 묶으면 안 된다.

당일 초기 글꼴 검증 보고서에는 보안 모듈 오류로 실패한 작업이 남아 있다. 이후 정상 조건의 실제 한글 출력 시험은 234개 입력 위치·15쪽 생성에 성공했고, 예시표 보정 후에는 279개 입력 위치·14쪽 생성까지 성공했다. 따라서 ‘그날 계속 실패했다’와 ‘모든 PC의 모듈 문제가 영구 해결됐다’ 모두 정확한 설명이 아니다. 초기 실패와 이후 실제 성공을 같은 기록에 남겨야 한다.

## 14. 자동 문서 작성 기능의 목표와 사용자 입력 축소

시작 사례는 기후부 2026 신청용 연구개발계획서였다. 처음에는 문서 안 작성요령을 빠짐없이 MD(Markdown, 간단한 텍스트 문서 형식)로 저장하고 서울과기대 탭에 전용 버튼을 두어 예시 내용으로 제출 문서 형태를 만들어 보려 했다.

사용자는 이후 사람이 매번 프롬프트를 복사해 외부 AI에 보내는 방식을 원하지 않았다. 프로그램이 소주제별 요령과 과제 정보를 모아 프롬프트를 만들고, 외부에서 로그인한 AI 에이전트에 차례대로 전달하며, 응답을 자동으로 받아 해당 문단에 넣도록 요구했다.

입력 화면도 점차 단순화했다. 사용자가 반드시 새로 입력할 값은 **작성 주제와 주제 세부 내용 두 가지**로 정했다. 문서 입력 정보 확인에는 개인 탭에 이미 저장된 값만 보여 주고, 빈 후보나 연결되지 않은 항목, 중복 행은 숨긴다. 동일한 개인 필드가 여러 문서 칸에 들어가면 화면은 한 줄로 묶되 대상 위치는 모두 보관한다.

최초의 여러 단계 확인 방식은 양식 선택과 작성 내용의 두 입력 단계로 정리했다. 이후 작업 중과 완료 후에도 입력값을 다시 볼 수 있도록 상단 네 단계와 하단 이전·다음 버튼을 다시 제공했다. 이는 입력 항목이 네 단계로 늘었다는 뜻이 아니라, 양식 선택·작성 내용·작업 진행·완료의 상태를 이동할 수 있다는 뜻이다.

작업 시작 이후에는 양식·주제·세부 내용·개인 값 수정이 실제 작성에 반영되지 않으므로 회색 읽기 전용으로 잠근다. 입력 당시의 사본을 저장해 나중에 개인 프로필이 바뀌어도 해당 작업에 사용된 값을 보여 준다. 진행 중 화면은 현재 처리 단계와 소주제를 표시하고, 완료 화면은 처리 요약과 최종 한글 파일 열기를 제공한다. 최종 사실·수치·증빙 검토는 출력본에서 수행한다.

## 15. 작성요령 추출과 MD 저장 방식이 바뀐 과정

처음 추출본에는 작성요령과 무관한 본문까지 들어갔다. 사용자는 ‘작성요령’이라고 적힌 표 안의 내용만 추출하고, 표 밖의 파란 주석에 있는 조건도 관련 주제의 요령에 합치도록 요구했다. 파란색이라는 이유만으로 모두 요령이 되는 것은 아니므로 원문의 제목·주제·조건 관계를 함께 보아야 했다.

파일을 너무 작은 소주제마다 나누지 말라는 요청에 따라 큰 번호의 대주제를 기준으로 파일을 나누되, 각 파일 안에는 소주제와 그 요령을 하나씩 남기는 방향으로 정리했다. ‘큰 주제로 파일 분리’가 ‘소주제 삭제’라는 뜻은 아니었다. 이후 번호가 있는 대·중·소주제와 상하위 요령 연결을 저장하도록 확장했다.

사람이 읽는 MD 정리본은 제목과 해당 작성요령 중심으로 두고, 원문 위치·필드 역할·해시 등 실행용 정보는 별도 파일에 저장한다. 작성 결과의 간단한 정리본도 ‘주제’와 ‘작성내용’ 중심으로 만들고, 원본 응답·출처·검토 사항·진행 상태를 별도 보관한다. 사용자의 ‘주제와 내용만 저장’ 요구를 모든 검증 자료 삭제로 해석하지 않았다.

상위 주제의 공통 조건은 그 아래 소주제에 전달하되, 형제 소주제의 전용 요령을 섞지 않는다. 연결할 주제가 불명확한 요령은 억지로 전체 공통 요령에 넣지 않고 미연결 상태로 보존한다. 같은 제목이 반복되어도 원문 위치로 구분한다.

### 15-1. 속도를 줄이려다 본문 위치를 놓친 시행착오

전체 문단을 AI에 보내 역할까지 분류하면 큰 양식에서 요청이 많고 시간이 오래 걸렸다. 원문을 text와 runs로 두 번 보내던 중복을 줄이고, 전체 문맥을 반복하지 않으며, 실패·누락 항목만 재검토하도록 최적화했다. 모의 시험에서는 전송 문자 수가 줄었지만 실제 비용이나 응답 시간이 같은 비율로 줄었다고 주장하지 않았다.

이후 소주제와 작성요령만 AI가 추출하고 빈칸은 프로그램이 연결하는 경로를 도입했다. 처리 범위는 줄었으나 본문 입력 위치가 부족한 양식이 있었다. ‘요령 MD 추출’과 ‘본문을 실제로 쓸 수 있는 양식 등록’을 혼동해 개인정보만 있는 등록본을 완료로 취급하면 안 된다는 문제가 드러났다.

9월 15일에는 전체 문단의 본문 연결을 복구한 중간 변경이 있었고, 같은 날 다시 요령 중심 등록으로 정리한 보고서가 뒤따랐다. 현재는 그 당시의 ‘AI는 빈칸 역할을 전혀 분류하지 않는다’는 설명에서 더 발전해, AI 입력 후보 분류와 표식 저장을 추가했다. 과거 노션 문서의 문구를 현재 설계라고 그대로 복사하지 않아야 한다.

## 16. 실제 외부 AI 연결 방식과 확인한 범위

현재 연결 코드는 Codex app-server를 별도 프로세스로 실행하고 표준입출력으로 구조화된 요청과 응답을 주고받는다. RPC(Remote Procedure Call, 다른 프로세스의 기능을 요청하는 방식)로 계정 확인·로그인·작업 시작·응답 수신·중단을 처리한다. 이 프로젝트의 ‘외부 AI’는 현재 이 연결 경로를 의미한다. ChatGPT 웹 화면을 몰래 조작하거나 응답을 화면에서 긁어오는 구현이라고 설명하면 안 된다.

작성할 소주제마다 새 임시 작업을 만들고, 필요한 이전 검증 결과만 명시적으로 전달한다. 양식 분석·본문 작성 요청은 제공된 자료를 사용하고, 자료조사 요청에서만 공개 웹 검색을 허용하는 코드가 있다. 개인 연결 서비스·로컬 파일 변경·구매·제출 등은 문서 작성 에이전트의 도구 범위에 포함하지 않는다.

2026-09-11 실제 연결 시험에서는 대주제 MD 안에서 ‘1-2. 국내·외 기술과 시장 현황’ 구역을 꺼내 전달했다. 표 요령과 파란 주석을 포함한 프롬프트 구역 447자가 저장된 MD 구역과 일치했다. 실제 AI 요청 1회로 기대한 8개 필드 모두 응답을 받았고, 누락·추가 위치 0개, 검토 항목 5개를 확인했다. 이 시험의 범위는 응답 수신·형식 검사까지였고, 그 시험 자체에서 전체 HWP 출력을 한 것은 아니다.

별도로 9월 15일 공개 주제 예제에서 실제 조사·작성 기록을 남겼고, 9월 28일 실제 연결 계정으로 양식 입력칸 분류를 시험했다. 저장 응답으로 출력만 시험한 작업은 외부 AI 새 호출 0회로 구분한다. 현재 통신 경로의 과거 성공과 모든 다른 계정·PC에서 같은 결과가 보장된다는 것은 다르다. 다른 환경은 사용 가능한 Codex 실행 환경과 로그인 상태를 갖춰야 한다.

### 16-1. 연결 해제가 PC 로그인까지 해제한 이유와 현재 남은 점

계정 표시와 연결 해제 버튼을 넣을 때 공식 account/logout을 호출했다. 이 방식은 범피스 화면의 연결만 끊는 것이 아니라 PC에서 공유하는 Codex 로그인에도 영향을 주므로 사용자가 문제를 제기했다.

**2026-09-29 소스 재확인 결과, AuthoringCommands._logout → CodexAuthor.logout → account/logout 경로가 여전히 존재한다.** 따라서 이 개인 기록에는 ‘앱 전용 연결 해제로 수정 완료’라고 쓰지 않는다. 앱의 연결 종료와 계정 로그아웃을 분리하거나 독립 인증 범위를 설계하는 일은 남은 개선점이다. 이번 노션 기록 작업에서는 실제 로그아웃이나 계정 변경을 수행하지 않았다.

## 17. 자료조사 범위와 본문·출처 분리

사용자는 문서에 넣을 문장만 쓰는 수준을 넘어 필요한 자료조사·분석·실행 방안까지 작성하도록 요구했다. 이후에는 자료조사가 과도하게 길어지지 않도록 최소한으로 하고, 본문 안의 출처 표시는 별도 자료로 분리하도록 조정했다.

구현된 최소 조사 정책은 중주제의 조사 결과 재사용, 문서당 최대 3개 조사 묶음, 조사 요청당 웹 작업 최대 6회와 출처 최대 3개를 요청하는 방식이다. 실제 도구 사용 횟수도 확인한다. 이는 자료조사를 전혀 하지 않는다는 뜻이 아니라, 필요한 근거를 제한된 범위에서 모아 본문 작성에 사용한다는 뜻이다.

출처는 삭제하지 않고 자료출처.json과 조사 보고서에 보관한다. AI가 받은 작성요령, 과제 주제·세부 내용, 해당 소주제의 입력 항목·분량, 관련 상위 조건, 이미 확인된 이전 결과, 조사 결과가 본문 작성의 근거가 된다. 개인 탭의 별도 저장값은 프로그램이 직접 입력하며 AI 요청에서 제외한다. 양식 원문 자체에 이미 들어 있는 정보는 분석 대상에 포함될 수 있으므로 별도 저장값 제외와 혼동하지 않는다.

근거 없는 성능·예산·인원·기관 실적·일정을 확정값으로 생성하지 않는다. 계획·제안과 이미 수행한 실측·성과는 구별한다. 정상 한글 파일 생성은 연구 내용의 진실성이나 제출 자격 검증 완료를 뜻하지 않는다.

## 18. 동일 양식으로 비교한 분석 성능과 사용량

## 19. 디자인·입력칸 분리와 표식 저장

사용자는 양식 전체의 디자인을 보존하면서 실제 입력해야 하는 곳에 대체 글자를 넣어 저장하고, 나중에 AI 응답이 오면 그 부분의 내용만 교체하도록 요구했다. 그러려면 양식을 등록할 때 제목·디자인·고정 문구·작성요령·개인정보·본문 입력칸·사실값 칸을 구별해야 한다.

처음에는 프로그램이 빈칸을 찾는 지역 규칙을 중심으로 연결했지만, 이후 AI가 후보의 의미를 보고 body(본문), personal(개인정보), factual(날짜·수치 등 사실값), preserve(원본 유지)로 분류하는 단계를 추가했다. 확신이 낮으면 review 상태로 남기고 자동 입력하지 않는다. AI는 원문에 없는 위치를 만들 수 없으며 문단 식별번호·중복·누락을 프로그램이 검사한다.

표 안에서는 같은 행·열의 항목명, 주변 문단, 상위 주제와 작성요령을 함께 제공한다. 제목 아래에 빈 문단이 여러 개 있다고 전부 본문칸으로 확정하지 않는다. 서명·직인·선택 표시·여백·장식 구조도 단순 빈칸과 구분한다.

9월 28일 실제 AI 분류 시험은 후보 272개에서 보존 36, 사실값 105, 개인정보 68, 본문 23, 검토 40개를 기록했다. 실제 AI 요청은 8회였고, 등록본에는 208필드와 196개 표식이 생겼다. 한 칸에 시험값을 넣어 실제 한글 저장·재열기·표식 제거·쪽 설정·표 수 보존을 확인했다. 이 시험은 한 칸 실입력 검증이지 208곳 전체 의미 정답 검증이 아니다.

후속 재검토에서는 기존 확정 결과를 다시 쓰고 불확실한 후보만 추가 문맥으로 분석했다. 실제 AI 요청 3회로 review 40개 중 33개가 해결되어 7개가 남았다. 남은 7개는 이미 확보한 다른 입력 위치로 해당 본문을 처리할 수 있어 사용자 별도 확인 수가 0으로 계산됐지만, 원문 판정 자체는 partial 상태였다. ‘사용자 확인 0’과 ‘불확실성 0’은 다르다.

### 19-1. 데이터베이스에는 무엇을 저장하는가

2026-09-28부터 등록 양식 폴더에 버전별 SQLite 데이터베이스를 저장했다. SQLite는 별도 서버 없이 파일 하나로 사용하는 데이터베이스다. 원본 HWP와 원본 구조, 등록한 입력 표식, 디자인과 내용의 역할을 함께 관리한다.

- metadata: 원본·입력 연결 검증값, 분류 버전, 등록 시각, 보호 문단 위치.
- design_layout: 교체할 내용과 요령 텍스트를 분리한 양식 구조. 글꼴·문단·쪽·표·도형·고정 항목을 보존.
- regions: 문단의 고유 경로, 표·셀 소속, 분류와 근거, 원문, 서식 참조.
- content_fields: 필드 식별번호, 주제, 원래 위치, 실제 입력 위치, 교체·뒤에 삽입·차단 방식.
- tables 및 cells: 표 중첩, 용도, 크기, 병합 등 구조.

표 전체를 단순히 입력용/디자인용 둘 중 하나로만 판단하지 않고 혼합 표에서는 셀·문단별로 구분한다. 출력 전에 원본과 데이터베이스·입력 위치 버전의 해시를 확인한다. 해시는 내용이 바뀌었는지를 확인하는 식별값이다. 기존 등록본을 강제로 바꾸지 않고 재등록·재연결 시 새 버전으로 저장한다.

실제 검증용 양식에서는 772문단, 22표, 553셀, 169필드를 저장하고 기존 보호 경로와 데이터베이스 경로의 출력 구조·입력 로그가 같음을 확인했다. 관련 시험 253개와 저장 응답을 이용한 실제 한글 생성 이력이 있다. 모든 새 양식의 의미 분류가 자동으로 정확하다는 보증은 아니다.

## 20. 양식 삭제에서 발생한 WinError 5

사용자가 등록된 양식을 지우려고 할 때 templates 폴더를 deleted_templates로 옮기는 중 ‘WinError 5, 액세스가 거부되었습니다’가 나왔다. 파일 권한만의 문제로 단정할 수 없어서 실제 권한과 파일 점유를 확인했다.

중간에는 이동이 실패하면 삭제 기록만 남겨 목록에서 숨기는 우회 처리를 만들었지만, 사용자가 오류 자체를 해결하라고 요구해 철회했다. 현재 기준은 실제 등록 폴더를 보관 위치로 옮겨야 성공이며, 단순 목록 숨김을 삭제 성공으로 처리하지 않는다.

사용자 등록 폴더에 필요한 접근 권한이 있었고 개별 파일 점유 검사에도 명확한 차단이 없었다. 별도 시험에서 하위 guides 디렉터리를 열어 둔 상태만으로 상위 폴더 rename이 WinError 5를 내는 경우를 재현했다. 이는 가능한 조건을 확인한 것이며 사용자의 실제 점유 프로세스를 특정했다는 뜻은 아니다.

수정은 먼저 원자적 폴더 이동을 재시도하고, 계속 WinError 5이면 정확한 등록·보관 경로와 연결 폴더 여부를 검사한 뒤 보관본을 복사하는 방식이다. 모든 파일의 SHA-256 해시와 폴더 구성을 비교하고, 복사 중 원본 변화도 확인한 다음 원래 등록 폴더를 정리한다. 중간 실패 시 보관본을 남기고 가능한 원본 복원을 수행하며 실패로 반환한다.

다른 앱을 강제 종료하거나 포괄적으로 권한을 바꾸지 않는다. 실제 하위 폴더가 열린 경우·배타적 파일 잠금·권한 거부·복사 실패·해시 불일치·부분 정리 실패 등을 시험했다. 삭제 보관본을 이용한 수동 복구는 가능하지만 모든 상황의 복원 버튼까지 완성된 것은 아니다.

## 21. 저장된 AI 응답 묶음과 재출력 기능

사용자는 매번 AI를 다시 호출하면서 표와 서식을 시험하는 대신, 이미 생성된 AI 응답을 하나의 파일로 모아 다른 폴더에 보관하고 같은 출력 기능을 시험하도록 요구했다.

초기 묶음은 `수소핵융합에너지_20260919_응답묶음.json`이다. 당시 완료 작업의 39개 주제 기록, 원래 AI 응답 29회분, 프롬프트, 입력 정보와 조사 기록을 모았다. 39개 주제와 실제 AI 요청 29회는 다른 집계다. 개인 값이 포함될 수 있는 내부 파일이므로 이 노션 기록에는 실제 이름·연락처·인증정보를 복사하지 않는다.

‘저장된 AI 응답으로 작성’ 경로는 새 AI 생성·자료조사·AI 재요약 없이 기존 문서 작성 서비스의 검증·문단·표·색상·한글 저장·재열기 처리를 그대로 사용한다. 원본 응답이 없는 주제를 새로 지어내지 않으며, 원본 양식과 필드 연결의 검증값이 맞지 않으면 중단한다.

새 양식을 등록한 뒤 ‘응답과 다르다’는 오류가 난 이유는 양식 이름만 같아도 실제 원문·입력 위치·필드 식별번호가 달라질 수 있기 때문이다. 같은 원본의 같은 위치는 확인해서 이전 응답을 옮기고, 바뀐 위치는 의미를 대조해 별도 묶음을 만들어야 한다. 보안상 맞지 않는 묶음을 억지로 통과시키는 방식으로 해결하면 잘못된 칸에 내용이 들어간다.

9월 29일에는 새 등록 양식용 묶음에 이어 예시표 보정용 v2 묶음을 만들었다. 최종 묶음은 32개 주제 구조에 맞췄고, 기존 목표 본문의 요지를 예시표의 29개 입력 항목으로 나눴다. 원래 없던 정량 실적을 창작하지 않았으며 성능 목표값 두 칸은 확인 필요로 남겼다.

## 22. 본문이 ‘확인필요’로 사라진 문제와 복원

사용자는 확인 필요 표시를 짧게 줄이길 원했지만, 초기 처리에서는 확인 문구가 있는 칸 133개를 통째로 바꾸어 AI가 작성한 본문까지 사라졌다. ‘검토 안내 간소화’와 ‘본문 삭제’를 구분하지 못한 과도한 치환이었다.

9월 22일 백업한 원래 AI 응답에서 표 밖 본문과 표 안의 목표·설명·계획 등 서술형 내용을 복원했다. 본문에 섞인 자세한 확인 사유만 별도로 분리하고, 기관 실적·시장 규모·금액 등 제공되지 않은 사실값 칸을 따로 처리하도록 바꿨다. 표 안에 있다는 이유만으로 그 내용을 모두 사실값이나 빈칸으로 취급하지 않는다.

기본 출력색은 검은색으로 두고, 처음에는 확인 부분만 파란색으로 표시했다. 다음에는 해당 문단 아래에 괄호로 된 파란 확인 안내를 두는 방식으로 바뀌었다. 본문과 검토 사유를 분리하면서 사용자가 작성된 글을 읽을 수 있게 하는 목적이었다.

이후 한글의 메모 기능을 연결했다. 본문을 직접 바꾸지 않고 옆에 무엇을 어떤 자료로 확인하면 좋을지 남기도록 했다. 메모가 너무 많다는 피드백에 따라 단순 빈칸·이름·연락처·미정 수치의 입력 안내에는 메모를 만들지 않고, AI가 실제로 작성한 본문 중 검토 사유가 있는 곳에만 연결했다.

실제 9월 22일 시험에서 메모가 133개에서 본문 검토용 31개로 줄었고 빈칸 메모는 0개였다. 169개 필드의 본문 내용이 이전 출력과 같음을 비교하고 실제 저장 후 메모·위치·서식을 재검증했다. 메모는 필드마다 무조건 생성하는 것이 아니며 최신 예시표 시험의 메모 수는 0개다. 과거 31개 메모 시험을 최신 14쪽 출력에도 그대로 적용된 결과라고 쓰지 않는다.

## 23. 디자인용 표에 본문이 들어간 원인과 보호

처음에는 폭이 좁은 숫자칸·간격칸만 디자인으로 막았다. 그러자 넓은 제목 셀이나 ‘최종목표’, ‘세부목표’ 같은 고정 항목명 셀을 본문 위치로 잘못 사용했다. 입력칸이 없을 때 제목 바로 뒤에 문단을 추가하는 처리도 표 셀 내부에 본문을 만드는 원인이었다.

수정 후에는 번호 배지·간격·짧은 제목이 한 줄로 구성된 제목 막대 전체를 보호한다. 제목 막대의 본문은 그 표를 포함한 문단 뒤에 만든다. 일반 표에서 왼쪽 고정 항목명과 오른쪽 내용칸이 나뉘면 항목명을 유지하고 실제 내용칸에 연결한다. 표가 넓거나 비어 있다는 이유만으로 전체를 디자인으로 막지는 않는다.

입력 표·디자인 표·혼합 표·정적 보존 표를 구분하고, 출력 직전 보호 문단이 바뀌었는지 검사한다. 저장된 응답에 임의 위치가 들어 있어도 이 보호를 우회할 수 없도록 원본 양식에서 목적지를 확인한다.

당시 실제 시험에서는 제목 막대 3개를 유지했고, 두 본문을 제목 막대 밖으로 옮기고 두 항목명 칸의 본문을 오른쪽으로 옮겼다. 원본 표 22개와 기존 169개 필드 본문, 31개 메모를 확인했다. 이후 ‘예시 내용이 있는 입력용 표’를 고정 표로 취급하는 반대 방향의 누락 문제가 발견되어 9월 29일 다시 보완했다.

## 24. 작성요령 표가 빈 껍데기로 남은 문제

출력 시 작성요령의 텍스트만 지우면 빈 표 틀이 남아 문서가 지저분해졌다. 작성요령 표는 텍스트 삭제 전에 원문 상태에서 식별하고, 순수 안내 표로 확인되면 표 개체 자체를 제거하도록 했다.

다만 표 안에 실제 입력 필드나 보호할 제목이 섞여 있으면 표 전체를 지우지 않는다. 안내용 예시의 하위 표·도형을 정리하되 실제 본문 표의 구조는 보존한다. 예시 도형을 삭제해 불필요하게 큰 행이 남으면 관련 높이도 정리한다.

이 조치는 빈 안내 표 제거와 실제 내용 표 보존을 함께 검사해야 한다. 최신 9월 29일 예시표 출력 보고서의 남은 작성요령 표 수는 0으로 기록되어 있다.

## 25. 표 내용·본문 문단·글꼴 정리의 변화

### 25-1. 표가 넘치지 않게 하는 분량 처리

사용자는 표 내용도 본문처럼 문단을 나누고 정렬하며, 셀 크기에 맞춰 내용이 다 보이게 하라고 요구했다. 셀 폭·높이·안쪽 여백·적용 글자 크기·문단 간격으로 예상 글자 수와 줄 수를 계산해 작성 요청에 전달했다. 한 셀에 여러 필드가 있으면 공간을 나누고 고정 문구와 직접 입력값이 차지하는 공간을 제외한다.

새 AI 응답이 예상 분량을 초과하면 한 번 요약 재작성을 요청한다. 원래 숫자·날짜·검토 사유나 다른 필드까지 바뀌면 수용하지 않는다. 재작성 후에도 초과하면 원래 응답과 오류를 남긴다. 저장 응답 재사용에서는 새 AI 요약을 하지 않고 경고를 남긴다. 문자열을 잘라 성공 처리하지 않는다.

설명문은 왼쪽·위쪽 정렬, 금액·수량은 오른쪽 정렬, 짧은 값과 개인정보는 원본 조건을 존중한다. 문단 앞 여백·줄 간격·셀 안쪽 여백을 조정하고 목록은 내어쓰기로 둘째 줄을 내용 시작 위치에 맞췄다. 처음 시각 검증에서 발견한 내어쓰기 단위 오류도 보정한 이력이 있다.

### 25-2. 문서 중간에 글꼴이 바뀐 문제

빈 문단·제목·작성요령의 남은 서식을 본문이 물려받아 글꼴과 크기가 흔들렸다. 한때 표 안과 표 밖을 각각 하나의 대표 글꼴로 통일했지만, 사용자는 원문 본문에서 실제 서식이 바뀌는 곳은 그 변화를 따라가야 한다고 요청했다.

이후 본문 흐름에 따라 글꼴을 상속하게 바꿨다. 실제 본문과 명시된 지시를 기준으로 변경 지점을 잡고, 빈칸의 잔여 서식·제목·작성요령은 변경 근거에서 제외했다. 별도 표 서식이 없으면 해당 위치의 본문 서식을 사용한다.

9월 29일에는 실제 표에 있던 입력 글꼴이 무시된다는 피드백에 따라 표의 명시 지시 → 원래 값이 있던 입력칸의 서식 → 빈 입력칸의 원래 서식 순으로 우선해 같은 표 안 입력값을 맞추는 쪽으로 보완했다. 표 전용 서식은 다른 표나 바깥 본문으로 전파하지 않는다. 고정 제목·라벨의 글꼴은 별도 유지한다.

### 25-3. 자간과 가운데점 줄바꿈

처음에는 단어가 중간에서 끊기지 않도록 어절·단어 유지 줄바꿈과 소폭 자간 축소를 적용했다. 이후 확대와 축소를 모두 고려하되, 사용자의 최종 요청에 따라 축소를 먼저 비교하고 보기 좋지 않을 때 제한적으로 확대한다. 새 보정 범위는 대체로 원본 대비 -5%~+5%이며 짧은 한 줄을 억지로 채우지 않는다.

‘연구·개발·검증’처럼 가운데점으로 연결된 문자열이 한 덩어리로 취급되는 문제에는 가운데점 뒤에 U+200B라는 폭 없는 공백을 넣어 그 자리에서 줄바꿈할 수 있게 했다. 보이는 공백이나 하이픈을 새로 넣는 방식은 아니다. 입력값 검사는 이 보이지 않는 표식을 제외하고 비교한다.

표도 같은 생성 문단 처리 정책을 사용한다. 다만 실제 줄 배치는 한글이 결정하며, 프로그램의 줄 수·폭 계산은 보수적 추정이다. 실제 지면 확인 없이 모든 표에서 완벽히 맞는다고 보장하지 않는다.

### 25-4. 표 너비 재배분

셀 내용이 넘치고 다른 열에 여유가 있을 때 단순 표의 열 폭을 조금 재배분하는 처리를 넣었다. 병합·중첩·그림이 없는 표를 대상으로 하고 전체 표 폭·행열 수·테두리·병합 구조는 유지한다. 폭을 받는 열은 최대 약 30%, 주는 열은 약 20% 이내로 제한하며, 다른 열의 내용이 더 넘치면 적용하지 않는다.

실제 등록 양식의 많은 표는 병합 구조이거나 여유 열이 없어 변경되지 않았다. 단순 표 예제의 폭 보존 검증과 실제 모든 양식의 자동 너비 보정을 혼동하지 않는다.

## 26. 수식·전력 단위·원소 표기

사용자는 계산식과 전력 단위·분자식도 문서용 표기로 바꾸도록 요구했다. 새로 작성된 본문과 표에서 아래첨자와 연산자가 있는 명확한 계산식을 찾아 한글에서 편집 가능한 수식 개체로 바꾸었다. 예를 들어 P_net=P_gross-P_aux 같은 식의 아래첨자를 수식 문법으로 전달한다.

수식 개체는 내부 줄바꿈이 어려우므로 셀 폭의 약 85%를 넘을 것으로 예상하면 일반 글자로 남긴다. 짧은 값 비교를 무조건 수식으로 바꾸거나 식의 결과를 계산해 만들어내지 않는다.

MW_th·MW_e·kWth·MWe의 th/e는 아래첨자, H2·H2O·CO2 등 지정 분자식의 숫자는 아래첨자, m^2·m^3 등의 지수는 위첨자로 표시한다. Unicode 대체 문자로 바꾸어 글꼴이 튀지 않도록 원래 글꼴 모양을 복제한 문자 서식을 사용한다. 불명확한 약어·사용자 직접 값·원본 고정 문구를 무조건 변환하지 않는다.

9월 29일 최종 예시표 출력 보고서에서는 수식 개체 2개, 아래첨자 서식 1개, 위첨자 서식 2개를 확인했다. 이 개수는 생성 구조의 개수이며 모든 학술 수식 문법을 지원한다는 뜻은 아니다.

## 27. 가장 최근 문제: 예시가 채워진 입력용 표를 고정 내용으로 오인

### 27-1. 사용자가 발견한 현상

2026-09-29 사용자는 출력본의 일부 표가 채워지지 않은 것을 확인했다. 원본 양식에 이미 예시 내용이 들어 있어 프로그램이 완성된 내용으로 판단하고 입력칸으로 비우지 않은 것 같다고 지적했다.

실제로 후보 추출 함수는 빈 문단과 명시적인 빈칸 표식 위주로 찾고 있었다. 글자가 들어 있으면 일반적으로 고정 내용으로 제외했다. 원본의 목표·성능·기술·적용 범위 예시와 중첩 성능 표가 입력 후보에서 빠졌고, 이전 과제의 얼굴·지문 인식, IPv6, 시험 지표 같은 문구가 남았다. YYYY·yy.mm·yy 같은 날짜 예시도 일부 남았다.

### 27-2. 코드 수정

`services/ai_input_slots.py`에서 반복적인 ‘(예)’와 ooo 같은 예시 표시가 있는 표를 후보로 찾고, 그 안의 중첩 표와 날짜 표식도 분석 대상에 포함하도록 했다. 이 수정은 모든 글자가 있는 표를 자동으로 비우는 방식이 아니다. 프로그램은 후보를 넓히고, 분류 단계에서 제목·고정 항목·예시 답변을 구별하도록 한다.

AI 분류 요청에도 ‘예시가 적혀 있다는 이유로 완성된 값으로 보존하지 말 것’, ‘표 제목과 고정 머리글은 보존하고 교체할 예시 답변은 입력칸으로 볼 것’을 명시했다. 기존 확정 판정은 재사용하고 새로 발견한 후보만 추가 분석할 수 있도록 재검토 경로를 바꿨다.

`services/template_guide_registration.py`에서는 예시 셀의 라벨을 이전 셀의 예시 문구로 덮어쓰지 않고, 검토한 의미 라벨을 유지하도록 했다. 새로운 본문·개인정보·사실값 입력칸이 발견되면 기존 불확실 항목 해결 여부와 별개로 새 등록본을 만들도록 했다.

현재 일반 후보 탐지는 반복 예시 표시와 날짜 패턴 등 명시적 근거에 의존한다. 예시 표시가 전혀 없는 다른 양식의 모든 채워진 문장을 자동으로 예시라고 정확히 구별하는 기능까지 완성된 것은 아니다.

### 27-3. 실제 등록본·응답 묶음 보정

원본 등록본은 유지하고 `연구개발제안서 · 예시표 입력 보정`을 새로 만들었다. 등록 식별자는 `0f5546b4e37e4f0db1eed5daf75abd06`이다.

최종적으로 예시 본문·표 위치 29개와 날짜·연도 예시 17개, 총 46개를 새 입력 대상으로 연결했다. 고정 라벨 9개는 보존했다. 이전에는 제목 뒤 한 자리 P0461에 넣던 본문을 실제 표의 항목으로 분배하면서 그 삽입 자리 하나를 제거했다. 그래서 전체 필드 수는 234 + 46 - 1 = **279개**가 됐다.

수정 등록에는 원본 해시와 정확한 문단 위치를 확인한 로컬 검토 규칙을 사용했다. 이 보정 과정에서 새 외부 AI 분류 호출은 수행하지 않았다. 한 차례 외부 전송 시도는 자동 승인 검토에서 원문 일부 전송의 별도 승인 근거가 부족하다고 거절되어 실행되지 않았고, 로컬 방식으로 보정을 완료했다. 원문 예시를 외부 AI가 새로 판단했다고 기록하면 안 된다.

- 이 최신 출력은 실제 한글 생성·읽기 검증을 했으나 14쪽 전체 화면을 이번 수정에서 다시 시각 검수한 것은 아니다.
- 최신 등록 상태는 partial이며, P0197은 항목명 주변의 빈 문단이 독립 입력칸인지 불명확해 사용자 검토 대상으로 1곳 남아 있다.
- 최신 검증 파일의 메모 수는 0이고 memos_verified=false다. 이 파일로 메모 기능까지 재검증했다고 하지 않는다.

## 28. 현재 문서 작성 전체 흐름

### 28-1. 새 양식 등록

1. 사용자가 서울과기대의 문서 작성 화면에서 저장된 양식을 확인한다.
2. 원하는 양식이 없으면 새 한글 양식 등록을 실행한다.
3. 프로그램이 원본 한글 사본과 구조 데이터를 추출한다.
4. 주제 번호·제목·작성요령 표·표 밖의 관련 파란 주석을 연결해 계층과 요령 문서를 만든다.
5. 입력 후보는 빈칸·명시 표식·예시가 채워진 표 등을 포함한다. 주변 의미를 보고 본문·개인정보·사실값·보존으로 분류한다.
6. 제목·디자인·고정 라벨을 보호하고 원문 위치와 서식 참조, 입력 표식을 저장한다.
7. SQLite 분리 저장본과 검증값이 준비된 뒤 등록 목록에 공개한다.
8. 불확실한 후보는 별도 검토하거나 기존 본문 위치로 해결 가능한지 확인한다. 재분석은 새 등록본을 만들어 이전 작업 사본을 보존한다.

### 28-2. 사용자가 문서 작성 시작

1. 등록 양식을 선택한다.
2. 작성 주제와 주제 세부 내용을 입력한다.
3. 개인 탭에 저장돼 정확히 연결되는 값만 트리 표에서 확인하고 필요한 경우 이번 작업 값만 수정한다.
4. 연결 계정을 확인하고 작성 시작을 누른다.
5. 프로그램이 입력값과 양식의 작업 사본을 저장하고 이후 편집을 잠근다.
6. 필요하면 제한된 공개 자료조사를 수행하고 결과를 소주제끼리 재사용한다.
7. 각 소주제에 해당 요령·상위 공통 조건·입력 항목·분량·과제 요청·관련 근거를 조합해 AI에 요청한다.
8. AI 응답의 필드 누락·중복·허용 위치·형식·길이를 검사한다.
9. 프로그램이 개인 값·사실값과 AI 본문을 구별해 연결된 자리에 넣는다.
10. 작성요령 제거, 디자인 보호, 문단·표 정렬, 글꼴 상속, 자간·줄바꿈, 수식·특수 표기, 필요한 본문 메모 처리를 수행한다.
11. 실제 HWP 파일을 저장하고 다시 읽어 입력값·위치·쪽 설정 등을 검사한다.
12. 완료 화면에서 수행 요약과 최종 파일을 연다. 사용자는 최종 사실·수치·증빙·레이아웃을 확인한다.

### 28-3. 저장 응답으로 재출력

등록 양식과 응답 묶음의 원본·필드 연결 검증값을 먼저 확인한다. 일치하면 외부 AI 호출 없이 같은 출력 경로를 사용한다. 일치하지 않으면 같은 이름이라는 이유로 우회하지 않고 새 양식에 맞는 응답 연결이 필요하다고 안내한다. 중단·실패 시 저장된 응답과 작업 상태를 이용해 원인을 확인하고 재개한다.

## 29. 작성 작업의 파일과 기록은 어디에 남는가

개발 실행의 주요 저장 루트는 `new_project/config/document_authoring/`이다. 내부 설치 환경은 사용자별 데이터 루트를 사용할 수 있으므로 모든 실행 환경을 개발 폴더와 동일하게 설명하면 안 된다.

```text
document_authoring/
├─ templates/<양식 식별자>/
│  ├─ template.hwp                  원본 한글 사본
│  ├─ source_original.hwpml         등록 전 원문 구조
│  ├─ source.hwpml                  입력 표식 등을 반영한 등록용 구조
│  ├─ manifest.json                주제·필드·정책·검증값
│  ├─ guides/                      작성요령과 원문 위치
│  ├─ 입력위치.json
│  ├─ 입력칸판정.json
│  └─ layout_<식별자>.sqlite3        디자인·내용 분리 저장
├─ jobs/<작업 식별자>/
│  ├─ state.json                   상태·사용한 입력 사본
│  ├─ template/                    작업 당시 양식 사본
│  ├─ prompts/                     실제 요청문
│  ├─ responses/                   응답·재시도 기록
│  ├─ research/                    조사 기록
│  ├─ 자료출처.json
│  ├─ 주제별_작성내용.json
│  ├─ 직접입력값.json
│  ├─ 입력필드.json
│  ├─ 확인메모.json
│  ├─ 자동검사.json / 검토사항.md
│  ├─ 작성중.hml
│  └─ 연구계획서_검토초안_*.hwp
└─ deleted_templates/              복구 가능한 삭제 보관본
```

모든 작업·버전이 위 파일을 전부 갖는 것은 아니다. 새 정책에서 추가된 파일과 예전 작업의 파일 구성을 구분한다. 한글 변환에 실패했더라도 AI 응답과 작성중 구조가 남아 있으면 내용을 확인하고 다시 출력할 수 있다. ‘파일 열기 실패’, ‘한글 저장 실패’, ‘AI 작성 실패’를 상태 기록으로 나누는 이유다.

## 30. 연구개발 작성 사례와 시각자료 기억

9월 25일 사용자는 연구개발계획서·제안서 작성 시 공통 문구만 반복하지 말고 실제 사례의 과제 성격과 소주제별 전개 방식을 참고하도록 기억을 요청했다. AGENTS.md는 작성 또는 작성 기능 설계 전에 AUTHORING_REFERENCE_MEMORY.md를 읽도록 연결한다.

기억에는 원문 제목·출처·과제 성격·연구내용·설명 전개·참고 소주제·필요 입력정보·확인 범위를 남겼다. 현재 연결 목록은 기존 사례 40건과 정보통신 50건으로 90건이다. 초기 자료는 공개 초록 중심이며 모든 제출 계획서 전문을 읽은 것으로 표현하지 않는다.

사진·표·그래프·도식에 대해서는 90건의 원문 PDF를 확보하고 공개 목록 4,947개, 실제 지면 개요 검토 596쪽, 전체 10,333쪽의 텍스트·구성 기계 점검 기록을 남겼다. 공개 목록의 위치 대조, 캡션에 근거한 추정, 직접 본 지면, 아직 보지 않은 범위를 구별한다. 모든 그림을 하나씩 정독·검증했다는 의미는 아니다.

실제 적용 기준은 ‘소주제에서 설명하려는 목적 → 삽입 위치 → 표·도식·사진 등 형식 → 필요한 실제 자료 → 출처와 미확정 상태’다. 자료가 없으면 보완 대기·계획 도식·평가계획·생략 중 적절한 방식을 택한다. 남의 실적·사진·측정값을 사용자의 성과로 바꾸지 않는다.

중요한 한계는 **이 기준을 기억 파일에 저장한 것과 프로그램의 모든 자동작성 프롬프트에 실제 연결한 것은 다르다**는 점이다. 현재 기억 문서에도 그 구분이 명시돼 있다. 자동작성 연결 완료 여부는 별도 구현·시험 근거로 판단해야 한다.

## 31. 함께 진행되거나 요청된 주변 작업

- 사용자 확인용 예시 한글 파일을 두 개 만들고, 한 파일 안에서 여러 기능을 비슷하게 확인하되 내용은 다르게 구성하라는 요청이 있었다. 이후 사용자가 프로젝트의 ‘범피스 예시1, 2’를 마련해 수정하도록 했다. 이 기록에서는 해당 두 파일의 최종 전 기능 검증을 새로 수행하지 않았다.
- 보기변환·비전표·분배 등은 실제 버튼과 예시 문서로 확인하려는 요구였다. 이름만 추정해 기능을 안내한 문제를 반복하지 않는 것이 중요하다.
- AI 문서·명단 명패·목차·보기변환·시험서식 영상 각각을 5MB 아래로 압축하고 노션 워크플로우 문서에서 보게 하라는 요청이 있었다. 이번 정리에서 해당 영상의 최종 업로드·재생 완료를 재검증하지 않았으므로 완료 성과로 확정하지 않는다.
- Windows 캡처 도구의 녹화 단축키·검은 화면·잘못된 창 녹화 문제를 논의했다. 프로젝트 내부 기능 오류와 화면 녹화 환경 문제는 구분한다.
- 프로젝트 전체 GitHub 푸시 요청이 있었다. 이번 작업은 과거 대화 기록 정리이며 원격 저장소 상태나 누락 파일을 재감사하지 않았다. 요청이 있었다는 사실과 전체 업로드 완료 증거를 구분한다.
- ChatGPT·Codex에 한글을 연결하는 MCP(Model Context Protocol, 외부 기능과 자료를 AI에 연결하는 규약), 공개 스킬·오픈소스 및 HwpForge 조사를 요청했다. 이후 구현 확인 근거는 현재 프로젝트의 한글 자동화·Codex 연결 코드이며, 대화에 이름이 등장한 모든 외부 도구가 통합됐다는 뜻은 아니다.

## 32. 현재 남아 있는 과제와 완료 판단 기준

1. **기관 운영 기능:** 기관별 패키지 구조와 실제 기관 인증·다운로드 서비스의 완성을 구분하고, 필요한 운영 흐름을 별도로 확정해야 한다.
2. **AI 계정 분리:** 현재 공유 account/logout 호출을 앱 전용 연결 해제와 분리하는 개선이 남아 있다.
3. **임의 양식 분석:** 입력칸 후보 누락과 예시 내용 오인 가능성이 남아 있다. 최신 양식의 P0197은 불확실하다.
4. **분석 속도·비용:** 특정 예제의 문자 수·요청 수를 모든 양식의 5분 완료나 실제 과금 절감으로 일반화할 수 없다.
5. **표 지면:** 병합·중첩·세로쓰기·그림·복잡한 표는 실제 한글 지면 검사가 필요하다. 자동 시험과 위치 검사가 시각 검사를 대체하지 않는다.
6. **메모 정책:** 본문 검토 메모는 실제 성공 이력이 있으나 최신 14쪽 출력에서는 메모 재검증이 이뤄지지 않았다.
7. **원본 동등성:** 소스 복구 1,511개와 정상 동등성 1,419개, 같은 오류 4개, 보류 88개를 계속 분리한다.
8. **사용자 요구 구현 상태:** 최상단 고정 선택, 기관 인증 등 논의만 확인되는 항목을 완료로 표기하지 않는다.
9. **연구개발 기억의 프로그램 연결:** 사례·시각자료 기준을 저장한 상태와 자동작성 실행에 연결한 상태를 별도 시험한다.
10. **실행 환경:** 바뀐 코드는 이미 실행 중인 프로세스에 자동 반영되지 않는 경우가 있다. 사용자 작업을 보존한 뒤 새 실행에서 확인해야 한다.
11. **제출 완성도:** 오류 없이 HWP가 만들어졌어도 사실·수치·증빙·기관 협의·실적·양식 적합성은 최종 검토해야 한다.

완료 기준은 코드가 생겼는지만 보는 것이 아니다. 원본과 입력 사본이 보존되고, 의도한 위치에 내용이 들어가고, 제목과 디자인이 유지되고, 결과 파일을 실제로 열 수 있으며, 불확실한 내용을 확정 사실로 바꾸지 않았는지까지 나누어 확인한다.

- **GUI — Graphical User Interface:** 버튼·창·탭으로 조작하는 화면.
- **WPF — Windows Presentation Foundation:** 현재 Windows 화면을 만드는 기술.
- **API — Application Programming Interface:** 프로그램의 기능을 호출하는 규약.
- **COM — Component Object Model:** Windows 프로그램의 객체와 기능을 다른 프로그램에서 호출하는 기술.
- **Automation 객체:** 한글의 문서 열기·입력·서식·저장 기능을 제어하는 연결 객체.
- **HWP / HWPX:** 한글 문서 파일 형식. HWPML은 한글 문서 구조를 XML 형태로 표현한 형식.
- **XML — Extensible Markup Language:** 요소와 속성으로 문서 구조를 기록하는 언어.
- **JSON — JavaScript Object Notation:** 필드·값·목록을 구조적으로 저장하고 주고받는 텍스트 형식.
- **MD — Markdown:** 제목·목록 등을 간단한 기호로 작성하는 문서 형식.
- **MCP — Model Context Protocol:** 외부 도구·자료를 AI에 연결하는 규약.
- **RPC — Remote Procedure Call:** 다른 프로세스의 기능을 요청하고 결과를 받는 호출 방식.
- **PID — Process Identifier:** 실행 중인 프로그램 프로세스의 식별번호.
- **DLL — Dynamic-Link Library:** 프로그램이 불러 사용하는 Windows 동적 라이브러리.
- **CLSID — Class Identifier:** COM 클래스의 식별자.
- **SQLite:** 별도 데이터베이스 서버 없이 파일로 저장하는 데이터베이스.
- **SHA-256 — Secure Hash Algorithm 256-bit:** 파일 내용 변경 여부를 확인하는 해시 알고리즘.
- **프리셋:** 미리 저장해 반복 사용하는 서식·내용 구조·연결 정보.
- **필드:** 문서나 사용자 데이터에서 값을 넣고 관리하는 항목.
- **스키마:** 데이터에 어떤 항목과 형식이 있어야 하는지 정한 구조.
- **스냅샷:** 특정 작업을 시작한 시점의 양식·입력값 사본.
- **픽스처:** 기능을 같은 조건에서 시험하기 위해 준비한 예시 문서·데이터.
- **회귀 시험:** 새 수정으로 기존 동작이 깨지지 않았는지 확인하는 시험.
- **모달/비모달:** 현재 창 처리가 끝날 때까지 다른 창을 막는 방식/다른 창도 조작할 수 있는 방식.
- **폴링:** 작업 상태를 일정 주기로 다시 물어보는 방식.
- **정적 일치/동적 일치:** 코드를 실행하지 않고 구조가 같음을 확인/실제 실행 결과가 같음을 확인.
