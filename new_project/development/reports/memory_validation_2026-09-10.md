# 화면 메모리 검증 — 2026-09-10

## 결론

검증한 격리 경로에서는 창·버튼이 정리 후에도 계속 남는 현상이 재현되지 않았다. 이전 실행에서 측정된 화면 프로세스 약 820MB의 원인과 전체 컴퓨터 멈춤의 원인은 아직 확정하지 못했다. 현재 자료만으로 컴퓨터 성능 부족 또는 메모리 누수를 확정해서는 안 된다.

## 실행 중 관찰의 한계

- 이전 대화의 실행 중 관찰: 화면 약 820MB, 기능 처리 약 40MB, 시스템 가용 메모리 약 3.5GB.
- 이번 검증 시작 시에는 해당 프로그램과 한글 프로세스가 발견되지 않았다. 20초 관찰의 유효 표본이 0개이며 별도 재확인에서도 실행 중 프로세스가 없었다.
- 실제 프로그램을 다시 실행하거나 창을 드래그하지 않았다. 실제 문서·개인정보를 읽거나 수정하지 않았다.

## 격리 반복 검사

`profile_memory_probe.ps1`에서 실제 함수만 불러왔다. 검사 당시 위치는 `tests/`였으며 검증 도중 외부 폴더 정리로 `development/tests/`로 이동한 것을 확인했다. 분석 결과는 예시 항목 12개로 대체했고 `ShowDialog()`는 실행하지 않았다. 결과 표와 메인 탭은 메모리 안에서 크기 계산·배치까지 수행했다. 실제 창 표시, 마우스 입력, 한글 연결, 그래픽 출력 경로는 포함하지 않는다.

각 확인 지점에서 대기 중 화면 정리 작업을 처리한 뒤 메모리 회수(GC, Garbage Collection)를 수행했다. 이는 객체가 회수 가능한지 확인하는 검사이며, 평소 실행 중 사용량이나 최고 사용량을 나타내지 않는다. 각 별도 프로세스에 20초·400MB 검사 한도와 30초 외부 종료 한도를 적용했다.

| 경로 | 5회 후 작업 메모리 | 30회 후 작업 메모리 | 30회 후 회수되지 않은 추적 객체 |
|---|---:|---:|---:|
| 개인정보 분석 결과 창 생성·정리 | 150.93MB | 138.96MB | 창 0개 |
| 기본 메인 탭 버튼 생성·제거 | 167.32MB | 173.25MB | 버튼 0개 |
| 비동기 응답 대기 처리 | 97.94MB | 98.27MB | 창을 생성하지 않음 |

같은 지점의 관리 메모리는 결과 창 11.64→12.77MB, 메인 탭 25.51→25.99MB, 응답 대기 11.11→11.14MB였다. 장시간 누수 여부를 판단할 정도의 기간은 아니며, 기관별 보조 창과 개인 탭 전체 흐름은 이번 탭 검사에 포함하지 않았다.

처음에는 화면 정리 대기열을 처리하지 않은 검사에서 닫은 창이 남아 보였다. 대기열 처리 후 모두 회수되었으므로 그 초기 결과는 누수 근거에서 제외했다.

## 이미지 파일 확인

- PNG 이미지 3,326개를 파일 헤더만 읽어 확인했다.
- 모든 파일을 동시에 4바이트 픽셀로 풀었을 때 약 272.58MB라는 계산값이 나온다. 실제 프로그램이 모든 파일을 동시에 읽는다는 뜻은 아니다.
- 이미지 버튼 생성 코드는 표시 크기에 맞춘 디코딩 크기 제한을 지정하지 않는다. 다만 이 사실만으로 실제 820MB 사용량의 원인이라고 단정할 수 없다.

## 남은 확인

실제 프로그램의 시작 직후 및 동일 작업 전후 메모리, 오래 사용한 뒤의 증가 추세, 실제 창 표시·그래픽 처리와 한글 연결이 포함된 상황을 따로 측정해야 한다. 전체 멈춤이 보고된 창 이동을 이번 검사 결과만 믿고 안전하다고 간주하지 않는다.

이번 작업에서는 진단용 검사와 이 보고서만 추가했으며 프로그램 기능 코드는 수정하지 않았다.

메모리 반복 검사 이후 기존 자동 검사 3개 모듈을 추가 실행하려 했으나, 그 사이 테스트 폴더가 이동하여 모듈을 불러오지 못했다. 해당 실행은 기능 검사를 수행하지 못한 것이므로 통과나 기능 실패로 집계하지 않는다. 외부 폴더 정리를 되돌리거나 그 변경과 겹치는 수정을 하지 않았다.
